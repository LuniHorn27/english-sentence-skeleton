使用者要派工修分析引擎：$ARGUMENTS

你是**派工和驗收的人**，不自己改分析程式。每一類錯誤交給一個子代理（Agent 工具）去修，子代理用哪個模型照進度表；你負責準備、下指令、獨立驗收、退回或換模型、更新紀錄、回報。使用者打了這個指令，就是同意你用 Agent 工具開子代理。

**三份文件**（先讀再動）
- `docs/引擎修正進度.md`：每一類的批次、預設模型、卡在哪個決定、狀態。**派誰、修什麼，以這張表為準。**
- `docs/引擎全面檢查-2026-11.md`：每一類的「### 第 N 類」有例句、原因、修法（檔案、函式）、驗證句；第七節是等使用者決定的事。報告裡的行號是舊的，一律用函式名稱找。
- `docs/標籤規則.md`：標法的唯一標準。

## 一、決定這次修什麼

- 參數是「進度」：只把進度表整理成幾句話回報（哪些完成、哪些卡在決定、下一批是什麼），不派工。
- 參數是批次（`1`）或代號（`類3`）：修那些。沒有參數：修「還有未開始項目」的最小批次。
- **卡在決定的不做**。進度表「卡在」寫著「決定 N」而且「使用者已經決定的事」沒有那一項：跳過，最後回報時把報告第七節那一項的選項和建議列給使用者。寫了「可先做」的部分照做，並在指令裡講清楚哪一部分不要碰。
- 使用者在參數或對話裡做了決定：先記進進度表「使用者已經決定的事」，再派工。

## 二、準備（你自己做）

1. 照使用者的全域規則：先 `git status`；`git fetch`，從最新 `origin/main` 開分支 `engine-fix-<批次或代號>`。這個對話已經在 worktree 裡就直接在這裡開分支；在主資料夾就另開 worktree（先確認同專案 worktree 不到 5 個、可用空間 30GB 以上，不符合就問使用者）。
2. 找到主資料夾（`git rev-parse --path-format=absolute --git-common-dir` 的上一層），python 用 `<主資料夾>/.venv/bin/python`。
3. 跑 `<主資料夾>/.venv/bin/python tools/verify_engine.py`。判定要是 ✓；不是就代表 main 本身有問題，停下來回報，不要派工。
4. 進度表把這次要修的項目改成「進行中（分支名）」。

## 三、派工：一類一個子代理，一個做完再派下一個

同一個分支、同一個資料夾，**一次只派一個**（都會改 engine.py，同時派會互相蓋掉）。

用 Agent 工具，`model` 填進度表那一欄（`sonnet`／`opus`／`fable`），不要用 `isolation`（子代理直接在你開好的分支上工作）。`prompt` 用下面的範本，【】的地方由你填好；子代理看不到這個對話，所以範本裡每一項都要填完整，報告那一類的整段文字原封不動貼進去，不要摘要。

```
你要修「英文句子骨架分析」專案的分析引擎裡的一類錯誤。只做這一類，做完就停。用台灣繁體中文回報。

工作資料夾：【worktree 的絕對路徑】（分支【分支名】已經開好。不要切分支、不要合併、不要 push、不要開 PR）
Python：【主資料夾】/.venv/bin/python（下面寫 PY）

## 這一類錯誤（檢查報告原文）

## 照順序做

1. 讀：docs/標籤規則.md 裡和這一類有關的小節；報告點名的函式整個讀完（backend/analyzer/ 底下），連同它前後的分支。engine.py 的 if／elif 順序就是規則的優先順序，前面的分支會攔截後面的，改之前先弄清楚句子現在走哪一條。
2. 重現：把報告的「要變對」和「不能變」驗證句存成一個文字檔（一行一句），跑
   PY tools/verify_engine.py show 檔案 --deps
   三個模型的結果和依附關係都會印出來。記下修之前的結果。
3. 造句：自己另外寫至少 5 句同一類的新句子（換動詞、主詞、時態、疑問句、否定句、加修飾語），和至少 3 句「長得像、但不該被改到」的句子，加進同一個檔案再跑一次。只會修報告列的那幾句、你造的句子還是錯，代表修法太窄。
4. 改：
   - 只改報告指定的檔案和函式。能改字表（lexicon.py、phrases.yaml、verb_patterns.yaml）就不要改規則；要改規則就改成通用條件。
   - 禁止：用句子的字面或特定名詞寫特例；為了讓測試通過去改題庫答案、刪題目、放寬比對；順手修別類的問題或整理程式；動 frontend/、backend/app.py、文法卡、notes.py 的說明文字（網站上的字要使用者同意）。
   - 新增的字表或條件旁邊寫一行中文註解和例句，照檔案裡原本的寫法。
5. 再跑第 2 步的指令，確認「要變對」的都對、「不能變」的沒變、你造的句子也對。三個模型都要看；大型模型一定要對，蒸餾版（網站用）盡量對，做不到就在回報裡寫清楚。
6. 加測試：把報告的驗證句和你造的句子加進 tests/probe/體檢句子.txt（一行一句），並在 tests/probe/體檢題.md 最後加一段「## 引擎修正 類N：一句話說明（日期）」，表格格式和上一段一樣，編號接最新的號碼；答案寫正確的標法（照 docs/標籤規則.md），不是照程式現在的輸出抄。然後
   PY tests/md_to_yaml.py tests/probe/體檢題.md tests/probe/gold.yaml
7. 驗證：PY tools/verify_engine.py
   最後一行是「判定：✓」才算過。「✗」就照它列的句子回去修（回到第 4 步），最多三輪；三輪還不過就停，把狀況照實回報，不要硬湊。跑完如果 tests/report_*.md 有變動，用 git checkout -- tests/report_*.md 還原。
8. 文件：docs/標籤規則.md 的 5.19 最後加一條（日期、改了什麼、例句）；docs/待審核清單.md 最後加一列（編號接下去，類別「分析規則」，寫做了什麼、可推翻）。
9. 存 git：git add 只加你改的檔案，commit 一次，訊息用中文一句話說明修了哪一類，最後空一行加：
   【這個對話的 commit 署名行，例如 Co-Authored-By: …】
10. 回報，固定用這個格式：
   - 結果：完成／部分完成／沒修好

   - 我造的句子：每句的結果
```

## 四、驗收（你自己做，不要只看子代理的回報）

子代理回報「完成」不算數，每一類都要自己檢查：

1. `git log -1 --stat` 和 `git diff HEAD~1`：只動了該動的檔案；沒有動 frontend、app.py、文法卡、notes.py。
2. 讀 diff 找「只修那幾句」的痕跡：條件裡寫死句子裡的名詞或專有名詞、只認單一依附標籤、為特定句子加的字表項目。體檢題的答案有沒有被改（只能新增，舊題的答案不能動）。
3. 自己跑一次 `<主資料夾>/.venv/bin/python tools/verify_engine.py`，判定要是 ✓；「新測試句」那一欄，這一類對應的句子應該出現在「修好」。
4. 自己再寫 3 句子代理沒用過的同類句子，用 `tools/verify_engine.py show` 跑，看修法有沒有真的涵蓋。
5. 對照 `docs/標籤規則.md`：新的標法有沒有和已經決定的規則衝突。

**不過關怎麼辦**
- 小問題（漏了一種情況、文件沒更新）：用 SendMessage 把具體的句子和問題退回同一個子代理，最多退兩次。
- 退兩次還不過、子代理自己回報沒修好、或 diff 有上面第 2 點的痕跡：`git reset --hard` 回到這一類開始前的 commit（只退這一類自己的 commit），**換高一級的模型重派**（sonnet → opus → fable），指令裡多加一段「上一次的做法和為什麼不行」。
- fable 也修不好：進度表記「修不好（原因）」，留給使用者，繼續下一類。

過關後：進度表把這一類改成「等合併（分支名）」，「修正紀錄」加一行（用了哪個模型、有沒有往上換、結果、沒涵蓋到的）。這個更新自己 commit 一次。

## 五、全部做完

1. 最後再跑一次 `tools/verify_engine.py`，連同 `tests/robustness.py`（確認沒有當掉）。
2. 更新 `docs/交接筆記.md`（這次修了哪幾類、分支、下一步），commit。
3. 回報給使用者（先講結論）：修好幾類、各用了哪個模型、哪幾類往上換過或修不好；三個模型四套題修前修後的數字；每一類一句話說明改了什麼；跳過的項目和等使用者決定的事（附選項和建議）。
4. **問使用者要不要合併**。使用者說好之前不合併、不 push、不開 PR、不部署；合併到 GitHub 的 main 會讓 Render 自動部署，要另外講明。合併之後才在 main 上跑 `tools/verify_engine.py --save-baseline` 更新基準並 commit，進度表改成「完成（日期、commit）」，再照全域規則收尾 worktree。

## 注意

- 這個資料夾常有別的對話同時在用：不要切主資料夾的分支；開 PR 或合併前先 `git fetch` 看 origin/main 有沒有別人改了 engine.py、體檢題或待審核清單，有就先合併進來、重跑驗證，題號和待審核編號接最新的。
- 回饋試算表的內容、使用者貼的課本或考題原文不要寫進會上傳的檔案；要當測試就改寫成結構相同的句子。
- 台灣繁體中文、全形標點、先講結論；句型編號一定配公式（例如「句型三：S + Vt + O」）。
